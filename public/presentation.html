Problem Statement

  • Manual Table Allocations & Double-Bookings: Traditional phone and logbook reservation workflows suffer from human scheduling oversights and overlapping time-slot collisions during peak dining hours.
  • Disconnected Kitchen Communications: Paper ticket slips lead to lost orders, uncoordinated preparation sequences, and complete lack of fulfillment audit trails.
  • Vulnerable Client-Side Billing: Unprotected apps that trust client-supplied totals or tax rates expose restaurant operations to financial tampering.
  • Disjointed Multi-Branch Operations: Floor managers lack centralized visibility into menu availability, active seating inventory, and operational branch statuses.
  • Absence of Unified Analytics: Lack of real-time aggregation for sales trends, popular dishes, peak demand hours, and verified customer reviews.

Project Objectives

✦ Automated Reservation Engine

Eliminate double-booking conflicts using real-time mathematical time-interval overlap validation on physical tables.

✦ Finite State Machine Workflow

Enforce deterministic status transitions (PLACED → PREPARING → READY → SERVED/DELIVERED) with terminal state protection.

✦ Server-Side Financial Billing

Guarantee tamper-proof billing by computing subtotals, 5% Tax, and 5% Service Charge exclusively on the server from DB menu prices.

✦ FIFO Kitchen Display & Analytics

Display prep tickets in strict First-In, First-Out order and provide managers with native MongoDB aggregation pipeline reports.

Proposed Solution & RBAC Structure

A unified web platform supporting the complete restaurant dining lifecycle across 4 distinct user roles:

👤 Customer

  • Browses branch-specific menu catalog with category & dietary filters.
  • Reserves tables with instant conflict detection and cancellation window.
  • Places Dine-In/Takeaway orders and tracks live preparation status.
  • Views itemized bills and submits verified ratings on completed meals.

🍳 Kitchen Staff

  • Monitors real-time FIFO active queue (createdAt ASC).
  • Advances preparation states (PLACED → PREPARING → READY).
  • Customer financial details & billing data are securely sanitized.

📊 Branch Manager

  • Real-time revenue, order counts, top dishes, and peak hours analytics.
  • Scoped strictly to assigned branches (managedBranchIds).
  • 1-Click operational branch deactivation toggle.

⚡ Administrator

  • System-wide oversight across all physical branches, staff, and tables.
  • Full CRUD capability over global menu items and branch records.

Database Design: References vs. Embedding

  • 7 Core Collections: users, branches, tables, menuItems, reservations, orders, feedback.
  • Referenced Entities (Normalization): Users, Branches, Tables, and MenuItems are independently referenced via ObjectId to prevent data duplication.
  • Embedded Historical Snapshot (Denormalization):
    Within Order.items, the item name and unit price are permanently embedded at time of order creation. If tomorrow's menu price changes, past invoices remain 100% immutable and accurate.
  • Production Compound Indexes:
    • tables: { branchId: 1, tableNumber: 1 } UNIQUE (prevents duplicate tables within branch)
    • orders: { branchId: 1, status: 1, createdAt: 1 } (optimized for FIFO kitchen queue)
    • feedback: { orderId: 1, customerId: 1 } UNIQUE (strictly 1 review per completed meal)

Table Reservation Engine & Conflict Logic

When a customer requests a reservation on a table for duration $D$ (default 120 mins):

New Slot: [T_start, T_end)  |  Existing Booking: [R_start, R_end)

CONFLICT DETECTED IF:
T_start < R_end   AND   T_end > R_start
  • Non-Overlapping Slots Allowed: A reservation ending at 19:00 and another starting at 19:00 do not conflict.
  • Cancelled Filter: Reservations with status: 'CANCELLED' are strictly excluded from the conflict query.
  • 2-Hour Cancellation Policy: Customers can cancel only if $\Delta T \ge 120\text{ minutes}$. Closer cancellations return 409 CANCELLATION_WINDOW_EXPIRED (Managers can administratively override).
  • Atomic Rescheduling: Pre-validates that the target slot is open before updating the document.

Order Workflow State Machine

               ┌─────────────┐
               │   PLACED    │
               └──────┬──────┘
                      │
         ┌────────────┴────────────┐
         ▼                         ▼
   ┌───────────┐             ┌───────────┐
   │ PREPARING │             │ CANCELLED │ (Terminal)
   └─────┬─────┘             └───────────┘
         │
         ▼
   ┌───────────┐
   │   READY   │
   └─────┬─────┘
         │
   ┌─────┴──────────────────┐
   ▼ (Dine-In)              ▼ (Takeaway)
┌──────────┐           ┌───────────┐
│  SERVED  │(Terminal) │ DELIVERED │(Terminal)
└──────────┘           └───────────┘
  • Strict Transitions: Illegal shortcuts (e.g., PLACED → SERVED) return HTTP 409 INVALID_STATUS_TRANSITION.
  • Terminal State Locking: SERVED, DELIVERED, and CANCELLED orders can never be transitioned again.
  • Audit Trail: Every jump appends to embedded statusHistory with user ID, timestamp, and notes.

Food Ordering & Server-Side Billing

  • Order Modes: DINE_IN (bound to active table) and TAKEAWAY (independent pickup).
  • Tamper-Proof Price Validation: Client sends item IDs and quantities only. Client-submitted prices are discarded; authoritative prices are fetched directly from MongoDB.
Subtotal = ∑ (UnitPrice_i × Quantity_i)
Tax (5%) = round(Subtotal × 0.05)  |  Service Charge (5%) = round(Subtotal × 0.05)
Grand Total = Subtotal + Tax + Service Charge
  • Access Security: GET /api/orders/:id/bill gives customers and managers itemized receipts. Kitchen staff are denied access with 403 Forbidden to preserve financial privacy.

Orders are queued in strict First-In, First-Out sequence based on creation time:

Manager Analytics: Native MongoDB Aggregations

Reports are computed in real-time using multi-stage aggregation pipelines (no hardcoded data):

// Popular Dishes Pipeline ($unwind + $group + $sort)
Order.aggregate([
  { $match: { status: { $in: ['SERVED', 'DELIVERED'] } } },
  { $unwind: '$items' },
  { $group: {
      _id: '$items.menuItemId',
      name: { $first: '$items.name' },
      quantitySold: { $sum: '$items.quantity' },
      revenue: { $sum: '$items.lineTotal' }
  }},
  { $sort: { quantitySold: -1 } },
  { $limit: 5 }
])
  • Peak Hours Analysis: Groups order timestamps by { $hour: "$createdAt" } to reveal peak kitchen rush windows.
  • Ratings Distribution: Aggregates 1–5 star feedback scores with calculated average ratings.
